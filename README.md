# happ-watchdog

Сторож для Happ VPN на Linux. Постоянно проверяет туннель, пингует серверы и
сам переподключает VPN при любой ошибке — обрыве связи, падении ядра, сбое DNS.

Зависимостей нет: только Python 3.11+ из системы.

```
happ-watchdog check      # разовая диагностика
happ-watchdog ping       # пинг серверов
happ-watchdog run        # мониторинг с автоперезапуском
happ-watchdog status     # что сейчас со сторожем
happ-watchdog stats 24h  # сводка по журналу: эпизоды, время без связи, виновники
happ-watchdog restart    # переподключить VPN руками
happ-watchdog pause 30m  # не вмешиваться полчаса
happ-watchdog resume
happ-watchdog install-service / uninstall-service

happ-fix-geo show        # какие geo-коды есть в профиле маршрутизации
happ-fix-geo fix         # дополнить недостающие (см. ниже)
happ-fix-geo restore     # откатить на резервную копию
```

**Запускать `run` можно только в одном экземпляре.** Второй берёт тот же файл
состояния и дерётся с первым: пока один делает `disconnect`, второй уже
`connect` — VPN разваливается, а общий лимит перезапусков выгорает за минуты.
Утилита держит `flock` на `run.lock` и вторую копию не пускает, подсказывая,
что делать со службой.

## Как часто проверяет

`interval = 10` секунд, `failures_before_restart = 3` — то есть сторож
вмешивается примерно через полминуты непрерывного сбоя.

Все пробы одного цикла идут **параллельно**, и это важно: они ждут не
процессора, а сетевых таймаутов. Последовательный прогон складывал таймауты в
одно окно, и когда туннель ложился по-настоящему, цикл растягивался на минуты —
между двумя «сбой N/2» в журнале проходило до 133 секунд вместо 20. Теперь цикл
длится столько, сколько самая медленная проба: около секунды на здоровом
туннеле и не больше `tcp_timeout` на мёртвом. Если цикл всё же вылез за полтора
интервала, сторож пишет об этом в журнал.

Отдельная засада была в системном резолвере: `socket.setdefaulttimeout` не
действует на `getaddrinfo`, и запасной путь проверки DNS мог думать десятки
секунд по правилам из `resolv.conf`. Теперь он выполняется в отдельном потоке с
жёстким сроком `dns_timeout`.

`startup_grace = 45` — пауза после появления Happ. Ядро `xray` и `sing-box`
поднимаются секунд за двадцать после старта GUI; без этой паузы сторож видел
«нет tun0, SOCKS refused» и слал `connect` прямо в момент запуска, то есть
дрался с самим Happ.

## Что проверяется каждый цикл

| Проверка | Как | Зачем |
|---|---|---|
| Аплинк | TCP/ICMP до шлюза из `/proc/net/route` | Если лежит Wi-Fi, VPN дёргать бессмысленно — сторож ждёт |
| Процессы и туннель | живы ли `xray` и `sing-box`, есть ли `tun0` с адресом | падение ядра или пропажа интерфейса |
| SOCKS | SOCKS5 → TLS → `GET /generate_204` через `127.0.0.1:10808` | сам туннель |
| Системный путь | тот же запрос напрямую, т.е. через `tun0` | маршрутизация всей системы, а не только прокси |
| DNS | сырой UDP-запрос A-записи к `1.1.1.1` / `8.8.8.8`, затем системный резолвер | ловит именно сбой DNS, когда TCP ещё жив |
| Системный DNS | резолв цензурируемого домена через резолвер из `resolv.conf` | путь браузера: ловит утечку DNS мимо туннеля |
| Ожидаемые коды | `[[checks.expect]]`, по умолчанию `api.anthropic.com → 404` | вмешательство в трафик к конкретному сервису |
| Логи Happ | всплеск ошибок в `~/.local/share/Happ/logs/*` | деградация до полного обрыва |
| Geo-файлы | есть ли в профиле маршрутизации нужные коды | из-за их нехватки ядро xray не стартует вообще |

Имя хоста в SOCKS-пробе резолвится на стороне прокси (ATYP=3), так что проба
заодно проверяет DNS внутри туннеля.

Проверка логов зависит от того, пишет ли их Happ вообще: сборка может держать
`tun_log.txt`/`core_log.txt` нетронутыми часами при живом ядре. Если ни один
файл не обновлялся в окне, сторож так и пишет — «логи не обновляются, проверка
не работает», а не бодрое «0 ошибок».

### Почему логи ядра пустуют (разбор)

На этой машине проверка логов неактивна, и вот что удалось установить:

- `tun_log.txt`, `core_log.txt` и `application_log.txt` не менялись с 12:58,
  хотя ядра с тех пор перезапускались (`xray` и `sing-box` живут с 15:28), а
  сам Happ — трижды. То есть дело не в одном сбойном запуске.
- `push_log.txt` и `subscription_log.txt` в том же каталоге пишутся исправно —
  каталог и права ни при чём, у Happ просто отдельные каналы логов
  (`addCoreLog`, `addTunnelLog`, `addMainLog`, `addPushLog`, …).
- Ни Happ, ни ядра не держат эти три файла открытыми — их сейчас не пишет никто.
- В бинарнике есть настройка `Preferences/LogSettings/xrayCoreLogLevel`, и в
  `~/.config/Happ.conf` её нет вовсе, то есть действует значение по умолчанию
  (среди возможных есть `none`).

Чтобы проверить версию с уровнем логирования, надо **закрыть Happ**, дописать в
`~/.config/Happ.conf` в секцию `[Preferences]` строку
`LogSettings\xrayCoreLogLevel=info`, запустить Happ и подключиться. Правка при
запущенном Happ бесполезна — он перезапишет файл своим состоянием из памяти
(та же оговорка, что и с `tunDnsEnable`).

Пока это не сделано, строка «Логи ядра Happ» в выводе — честная заглушка, а не
проверка. На остальные проверки это не влияет.

## Как чинит

Управление идёт через deeplink-и Happ (`happ://connect`, `happ://disconnect`) —
тот же путь, что и кнопка в интерфейсе, так что состояние Happ остаётся
согласованным. Лестница эскалации, ступень поднимается, если предыдущая не помогла:

1. `happ://connect` — мягкое переподключение
2. `happ://disconnect` → пауза → `happ://connect`
3. перезапуск процесса Happ и переподключение
4. `sudo -n systemctl restart happd` + перезапуск Happ — **выключено по умолчанию**
   (`allow_daemon_restart`), нужен беспарольный sudo

После каждой попытки сторож ждёт до `verify_timeout` секунд и проверяет связь
заново. Успех сбрасывает лестницу на ступень 1.

**Мягкие попытки (ступени 1–2) не ограничены ничем.** Сторож существует ровно
затем, чтобы не оставлять VPN лежащим, поэтому «сдаться» он не может: пройдя
лестницу, он уходит в фоновый режим и повторяет `disconnect → connect` раз в
`soft_retry_interval` (по умолчанию 5 минут), пока связь не вернётся.

Квота `max_escalations_per_hour` считается **только для жёстких шагов** —
тех, что убивают процесс Happ или демон. Крутить их по кругу вредно: если
причина не в туннеле (кончилась подписка, сервер мёртв, интернета нет), от
перезапуска GUI лучше не станет, а работать станет невозможно. Исчерпав квоту,
сторож пишет об этом один раз и продолжает мягкими попытками.

Плюс растущая пауза между попытками (`backoff`) и полный пропуск восстановления,
когда лежит физическая сеть.

## Браузер не открывает сайты при живом туннеле

Симптом: `curl` к api.anthropic.com отвечает как надо, Claude Code работает,
а YouTube и половина интернета в браузере не открываются.

Причина не в маршрутизации, а в DNS. Happ по умолчанию генерирует sing-box с
`"detour": "direct"` у DNS-сервера, то есть **запросы к 8.8.8.8 уходят мимо
туннеля**, через провайдера. Нецензурируемые имена резолвятся, и туннель
выглядит здоровым; цензурируемые (`youtube.com`) не резолвятся вообще —
одинаково у 8.8.8.8, 1.1.1.1, 77.88.8.8 и роутера, потому что режется сам путь,
а не конкретный резолвер.

Лечится штатной настройкой Happ:

```
~/.config/Happ.conf → [Preferences]
AdvancedSettings\tunDnsEnable=false
```

Happ пишет в лог `DNS detour set to 'direct' (tunDnsEnable=true)` — то есть
включённая настройка означает «свой DNS напрямую». Выключенная возвращает
`detour: proxy`, и DNS идёт через VPN. Правку надо делать при **закрытом**
Happ, иначе он перезапишет файл своим состоянием из памяти.

Российские сайты при этом не страдают: маршрутизация у них по доменам
(`geosite:category-ru`, `regexp:.*\.ru$`), и `ya.ru` с `gosuslugi.ru`
открываются за полсекунды.

Регрессию стережёт проверка «Системный DNS (браузер)»: она резолвит заведомо
цензурируемый домен через резолвер из `/etc/resolv.conf` — тот же путь, которым
ходит браузер.

## Сломанные geo-файлы профиля маршрутизации

Отдельная, самая неприятная поломка: профиль (у вас «ExtraVPN RU») приносит
собственные урезанные `geoip.dat`/`geosite.dat` — только с российскими кодами,
71 штука вместо полутора тысяч. Happ передаёт ядру `XRAY_LOCATION_ASSET` на
папку профиля, а конфиги серверов из подписки ссылаются на стандартные коды.
Не найдя кода, xray **не стартует вовсе**:

```
Failed to start: ... illegal domain rule: geosite:apple
                 > failed to check code APPLE from geosite.dat > EOF
```

В интерфейсе это выглядит как «подключился и сразу отвалился» — причём только
на части серверов, потому что рулесет приходит вместе с сервером из подписки.

`happ-fix-geo fix` дописывает недостающие записи из полных geo-файлов
`/opt/happ/bin/core`, сохраняя резервную копию. Коды профиля при совпадении
имён побеждают, так что российская маршрутизация остаётся ровно такой, какой её
задумал автор профиля — добавляются только отсутствующие.

Happ периодически перекачивает эти файлы по ссылкам из `routing.json` и ломает
их заново, поэтому сторож проверяет их каждые `[geo] check_interval` секунд и
чинит сам. Отключается через `[geo] autofix = false`.

## Ошибки в конфиге

Незнакомый ключ или секция не отбрасываются, но о них пишется предупреждение:
`inteval = 5` выглядит как настройка, а на деле оставляет `interval`
дефолтным — такую опечатку легко не заметить.

## Защита от драки с пользователем

- `only_when_gui_running = true` — если Happ закрыт, значит VPN выключен
  намеренно, сторож не вмешивается.
- `happ-watchdog pause 2h` — временно отключить вмешательство (например, чтобы
  посидеть без VPN). Снимается `resume` или само по истечении срока.

## Пинг серверов

`happ-watchdog ping` пингует TCP-коннектом всё, что знает о серверах:

1. `[servers] list` в конфиге — `host:port` или готовые ссылки
   `vless://`, `vmess://`, `trojan://`, `ss://`;
2. подписки из `[servers] subscriptions`, а если там пусто — URL-ы, которые Happ
   сам пишет в `~/.local/share/Happ/logs/subscription_log.txt`;
3. автоопределение активного сервера по установленным соединениям `xray`.

**Про подписки.** Оба ваших провайдера (`s.migapp.net`, `sub.luarity.ru`) отдают
стороннему клиенту заглушку `vless://…@0.0.0.0:1#Приложение не поддерживается` —
им нужен правильный заголовок `X-HWID`, который считает сам Happ. Поэтому полный
список из подписки не вытягивается; сторож это распознаёт и пишет предупреждение.
Чтобы пинговать все серверы, скопируйте ссылки из Happ в `[servers] list`, либо
подставьте свой `hwid` в конфиг, если узнаете его.

Автоопределение сервера неочевидно: `xray` держит соединения не только с
сервером VPN, но и с сайтами, которые роутинг отправляет напрямую. Сторож делает
два замера с паузой и оставляет адреса, которые держатся в обоих и собирают
существенную долю соединений (`discover_min_share`).

**Важно о цифрах пинга:** когда VPN поднят, весь трафик утилиты идёт через
туннель, поэтому пинг сервера — это latency «через туннель», а не прямая
задержка до него. Заголовок вывода честно пишет, каким путём меряли. Прямые
измерения получаются, когда VPN лежит, — то есть ровно тогда, когда это нужно
для диагностики.

## Сводка за период

`status` показывает срез «прямо сейчас», а `stats` — что происходило:

```
happ-watchdog stats 24h

  Эпизодов сбоя      : 28
  Времени без связи  : 37 мин (28.1%)
  Самый долгий       : 14 мин
  Прошло само        : 18
  Вылечено сторожем  : 6
  Попыток впустую    : 5
```

Плюс разбивка по шагам лестницы и по проверкам, которые падали чаще других —
видно, чинить ли DNS, маршрутизацию или подписку. Считается по журналу
(`watchdog.log` и `watchdog.log.1`), поэтому длительность эпизода известна с
точностью до одного цикла проверок.

## Тесты

```
python3 -m unittest discover -v
```

43 теста, меньше секунды, сети и настоящего VPN не касаются: пробы подменяются,
а `XDG_STATE_HOME` подставляется до импорта модуля, чтобы тесты не писали в
настоящий журнал. Покрыты разбор ссылок на серверы и DNS-ответов, слияние и
проверка конфига, лестница эскалации с квотой, логика утечки (включая пул
адресов провайдера и смену сервера между замерами), поиск `XAUTHORITY`,
поведение упавшей проверки и параллельный прогон.

## Автозапуск

```
happ-watchdog install-service
journalctl --user -u happ-watchdog -f
```

`install-service` запоминает в юните переменные текущей сессии
(`WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR` и т.д.) —
без них deeplink не дойдёт до графического Happ. Если вы поменяете тип сессии
(Wayland ↔ X11), выполните `install-service` заново.

`XAUTHORITY` — исключение: он в юнит не пишется. В Wayland-сессии он указывает
на `/run/user/1000/.mutter-Xwaylandauth.XXXXXX`, а этот файл создаётся заново
при каждом входе, так что записанный однажды путь протухает после первой же
перезагрузки. Сторож ищет самый свежий файл сам, перед каждым запуском Happ.

Остановка не ждёт пауз восстановления: `stop` доходит до всех ожиданий, так что
`systemctl --user stop` отрабатывает за доли секунды даже посреди лечения.
В юните на всякий случай стоит `TimeoutStopSec=30`.

## Коды возврата `check`

`0` здоров · `1` сбой · `3` нет физической сети
